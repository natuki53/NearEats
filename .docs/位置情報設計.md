# 位置情報設計
## 目的
現在地の緯度・経度から都道府県を判定し、その地域のご当地グルメカテゴリを表示する。

## 基本方針
Geolocation API で緯度・経度を取得し、逆ジオコーディングで都道府県を取得する。

## 逆ジオコーディングAPI候補
初期開発では LocationIQ を第一候補とする。
本番運用で住所精度や安定性を重視する場合は Google Geocoding API へ切り替え可能にする。

## APIキー管理
LocationIQ の Access Token は本番ではフロントエンドに直置きしない。
サーバー側の API プロキシ経由で LocationIQ に問い合わせる。

開発初期は動作確認を優先し、必要に応じてフロントエンドの環境変数で検証する。
ただし、公開時にはビルド済み JavaScript に Access Token が含まれない構成へ移行する。

## 処理フロー
1. ユーザーが「現在地から探す」を押す
2. Geolocation API で `latitude` / `longitude` を取得する
3. LocationIQ の reverse endpoint に `lat` / `lon` を渡す
4. `address.state` などから都道府県名を取得する
5. `localFoodCategories.prefecture` と照合する
6. カテゴリを表示する

## リクエスト・レスポンスイメージ
リクエスト:

```text
https://us1.locationiq.com/v1/reverse
  ?key=LOCATIONIQ_ACCESS_TOKEN
  &lat=33.5902
  &lon=130.4017
  &format=json
  &accept-language=ja
```

レスポンス:

```json
{
  "display_name": "福岡県福岡市...",
  "address": {
    "state": "福岡県",
    "city": "福岡市"
  }
}
```

## 都道府県名の取得優先順
LocationIQ のレスポンスに含まれる `address` から、以下の順で都道府県名を取得する。

1. `address.state`
2. `address.province`
3. `address.region`

都道府県名を取得できない場合は、県判定失敗として扱う。

## 失敗時の扱い
- 位置情報が拒否された場合: 通常検索へ誘導
- 県判定できない場合: 通常検索へ誘導
- 対応カテゴリがない場合: 準備中メッセージを表示

## 県境付近の扱い
都道府県判定は、逆ジオコーディングで取得した現在地住所の都道府県を採用する。
県境付近であっても、カテゴリ表示に使う都道府県は1つに固定する。

ただし、店舗検索は都道府県で絞り込まない。
現在地の緯度・経度と検索半径で取得し、検索半径内であれば隣接する都道府県の店舗も表示対象に含める。

## キャッシュ方針
同じ緯度・経度に対して毎回 LocationIQ API を呼ばない。
緯度・経度を小数第3位程度に丸めたキーで短時間キャッシュする。

例:
- `33.5902,130.4017` → `33.590,130.402`
- キャッシュ値: 都道府県名、市区町村名、表示用住所
